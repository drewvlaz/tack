Tack · Phase 2 + 3

Live updates architecture

How shared-board edits propagate in real time once the Durable Object transport lands. Phase 1 (shared boards with refresh-to-see) is in HEAD; this document scopes the live transport on top of it, including the surface added since Phase 1 shipped — multi-select batch ops, soft-delete / trash, reparse, primary-image, and the bookmarklet import path.

Overview

Two transports out of the browser, two classes of message, one Durable Object per board acting as broadcaster. The DO is purely a fan-out hub — D1 stays the only source of truth.

Persistent

Server-originated, broadcast after the db.batch() commit lands. Every persistent event carries a clientMsgId so the originating tab can suppress its own echo.

add new placement (URL parse or bookmarklet) patch geometry / z / primaryImageId — single or batch delete soft-delete one or more placements restore undo soft-delete from the trash drawer purge hard-delete from trash (R2 cleanup) replace reparse — full placement payload members.changed invite accepted / member removed kick targeted to the revoked user's sockets
Ephemeral

Client-originated, fanned out immediately by the DO, never persisted. Lost messages are lost — the next throttled emit covers the gap.

cursor pointer position, ~30Hz drag in-flight placement move, ~60Hz (one or many ids) resize in-flight width/height, ~60Hz ping presence keepalive

tRPC remains the only durable write path. The Durable Object holds zero persistent state — on restart, peers reconnect and resync via boards.getItems. Inside withTransaction, R2 cleanup and DO broadcast both ride the same Tx accumulator (scheduleBlobCleanup / scheduleBroadcast) and drain only after db.batch() commits. If SQL throws, neither runs.

Why Durable Objects

Workers are stateless and ephemeral — two peers on the same board could land on two different isolates with no shared memory. We need exactly one address per board where all connections converge. Durable Objects are Cloudflare's stateful primitive; ours is just the broadcast hub.

The constraint

A Worker invocation has no shared memory with its siblings. If Alice's WS connection lives on isolate A and Bob's lives on isolate B, there is no in-process place to keep "the list of connections for board X." Without a stateful coordinator, every broadcast would need an external message bus and the latency budget for cursors evaporates.

What a DO gives us

  1. Single-instance-per-name. env.BOARD_DO.idFromName(boardId) always resolves to the same DO instance. Every WS for that board converges there. Broadcast iterates state.getWebSockets() — no cross-isolate plumbing.
  2. Hibernation API. Cursor traffic is bursty-with-long-idles. state.acceptWebSocket() hands the socket back to the platform between messages and only wakes the DO on inbound traffic. Idle peers don't keep an isolate hot.
  3. Serialized writes. Method calls on a DO are processed one at a time. We don't have to coordinate concurrent broadcasts — the DO is its own ordering authority.

Why per-board (not per-user, not global)

One DO per board scopes traffic naturally. Cursor blast radius is exactly the set of peers on that board (small — usually 2–5). A noisy board can't degrade other boards' latency. Per-user would mean cross-multiplexing N boards through one DO with no clean fanout target. Global would funnel every cursor through a single CPU and cliff at low hundreds of users.

Alternatives we ruled out

Stateless Workers + external pub/sub
Redis / Upstash / NATS adds infra we don't own, costs money, and introduces a latency hop. Overkill for our volume.
Polling
Defeats the sub-100ms cursor target.
Server-Sent Events
One-way only (server → client). We need to send cursor and drag positions up.
WebRTC peer-to-peer
Still needs a signaling server, NAT traversal is brittle, and the security model gets complicated fast.
One global broadcaster Worker
Workers don't work that way. Even if they did, every cursor message would contend for one CPU.

Trade-offs we accept

  • ~30–50 ms cold-start on the first peer joining a board. The DO stays warm while anyone's connected.
  • Geographic pinning. A DO lives in one region. Cross-continent peers pay the extra round-trip. For a personal moodboard with small co-editor groups, peers usually cluster anyway.
  • Hibernation footguns. Per-socket data must go through serializeAttachment; instance fields don't survive between messages. Easy to get wrong on first attempt — documented as an invariant in the implementation plan.
  • Cost. DOs bill on requests + duration. For Tack's scale (single-digit boards, sub-100 concurrent users), pennies per month.

What the DO is NOT

The DO is not a database. It holds zero durable state. D1 is the source of truth. If a DO restarts (deploy, eviction, region failover), peers reconnect, re-issue boards.getItems, and life continues. This is invariant #1 below — it keeps the architecture safe to evolve.

Components

Two browsers, one Hono worker with a tRPC handler and a WS upgrade route, one DO per board, D1 + R2 as the durable substrate. After migration 0009 the canonical product record is the placement (board_items) — there is no separate items table.

Sequences

Seven flows. The first three carry the main load (mutations, cursors, drag/resize). The next three handle lifecycle (trash, connect, reconnect). The last revokes access mid-session.

Persistent Mutation (add, patch, delete — single or batch)

tRPC stages SQL, then schedules the broadcast on the same Tx accumulator. The broadcast carries the originator's clientMsgId, which Alice's browser uses to suppress the echo of its own optimistic update. Group ops (patchItemsMany, deleteItemsMany) carry an array under the same single broadcast — one atomic batch, one message.

Single vs batch shape. patchItem carries one { id, patch }; patchItemsMany carries { patches: [{ id, patch }] }. The broadcast mirrors the input: { type: 'patch', K, patches } in both cases (with length 1 in the single-patch path). Receivers iterate.

Ephemeral Cursor broadcast

Pure relay through the DO. No D1 write, no clientMsgId — the DO fans out to peers and skips the originator. Throttled to ~30Hz on the client side. The DO reads userId from the socket's serializeAttachment, set at upgrade time, so the client can't spoof identity.

Mixed Collaborative drag & resize

Two-phase: ephemeral while the gesture is in flight (60Hz messages move Bob's Card via motion values directly — no React state churn), then a single persistent patch on gesture end commits the final geometry to D1. Group drag fans the same shape with an array of ids; resize uses an identical envelope with width/height instead of dx/dy.

Persistent Trash · restore · purge · replace

Soft-delete sends a placement to the trash drawer; restore brings it back; purge (or emptyTrash) hard-deletes the row and reclaims R2 blobs. reparseItem and setPrimaryImage fold into the same envelope as a server-driven replace (full payload) or patch (single field), respectively — same commit-then-broadcast ordering.

Why replace instead of a richer patch. Reparse can churn metadata and images simultaneously. The wire shape is simpler if the broadcast carries the full payload than if receivers have to diff two image arrays. setPrimaryImage stays a patch with one field — primaryImageId — because that's all that changes.

Lifecycle Connect + initial sync

No special "sync" message — boards.getItems already gives the client a fresh snapshot. The WS opens against that snapshot and incoming patches are diffs from there. The bookmarklet import flow (/import) is the same: it lands users on a board, runs getItems, and only then opens the live socket.

Lifecycle Reconnect after disconnect

Exponential backoff up to 30s. On reopen, invalidate the items query so the client re-snaps from D1 — any patches missed during the outage are now in the snapshot.

Persistent Kick (membership revoked mid-session)

removeMember stages the soft-remove + a targeted kick broadcast. The DO finds Bob's specific socket(s) by attachment and closes with a non-retry code so the client doesn't auto-reconnect. The same shape covers leave — the leaver broadcasts members.changed but doesn't get a kick (they closed deliberately).

  autonumber

  participant W as Worker
  participant DO as BoardDO

  Note over W: withTx: requireOwner

  W->>DO: publish (both messages)
  Note over DO: for ws in getWebSockets():
  if attachment.userId == bob:
    ws.send({ kick })
    ws.close(4003) — non-retry
  DO->>Bob: WS { kick }
  DO-)Bob: WS close (4003)
  Note over Bob: onmessage: toast, clear activeBoardId, invalidate boards list
onclose: do NOT reconnect (clean code 4003)

Invariants

Properties the design has to preserve. Each one is encoded in either the file layout or the runtime ordering, not in convention.

  1. tRPC is the only durable write path.

    The DO never writes to D1. A DO restart loses nothing important — peers reconnect and resync via getItems.

  2. R2 cleanup AND DO broadcast both run after db.batch() commits.

    scheduleBlobCleanup and scheduleBroadcast are siblings in the Tx accumulator. If the batch throws, neither runs. Bytes can outlive rows (GC-reclaimed), but rows can never point at missing bytes — and a ghost broadcast can never reference a row that didn't commit.

  3. Echo suppression is clientMsgId-based.

    The client tags each mutation, the server echoes the tag through the broadcast, the originating tab ignores echoes with its own tags. No server-side per-connection memory required. Multi-tab same-user still receives the echo on the non-originating tab because sentMsgIds is per-tab.

  4. Authorization happens on the HTTP upgrade.

    The /live route resolves the session cookie to a userId and calls boards.requireEditor(boardId, userId) before forwarding the upgrade. The DO trusts attachment.userId because only that route can set it.

  5. Ephemeral messages never touch D1 and carry no clientMsgId.

    Lost cursor / drag / resize messages are lost — the next throttled emit covers the gap. No retransmit, no replay buffer.

  6. Presence is purely client-derived.

    Cursor and gesture entries are populated from inbound messages. A peer that quietly vanishes is culled after 5s of no traffic. presence_leave is a hint, not a contract.

  7. One withTransaction block, one broadcast (atomic with the batch).

    Every mutating procedure stages exactly one scheduleBroadcast. Batch ops (patchItemsMany, deleteItemsMany, emptyTrash) carry an array under that single broadcast — the user contract ("all or nothing") stays one-to-one with the wire shape.
